# GuDuu OS — 版本号升级规则

> 本文约定产品对外版本号怎么涨、涨完写哪、AI 提交时怎么记、怎么汇总成对外更新说明。
> 目标：**SemVer 语义可信**（OEM 敢升级）+ **PATCH/周报养维护感**（用户觉得一直在更新）。
> AI 全局摘要见 `.cursor/rules/versioning.mdc`；`CLAUDE.md` / `AGENTS.md` 有提交流程引用。

---

## 1. 对外主版本格式

**格式：`MAJOR.MINOR.PATCH`（标准 SemVer 语义）**

| 段 | 中文 | 何时涨 | 对 OEM 的含义 |
|---|---|---|---|
| `PATCH` | 小版本 | 有可交付改动时的**默认**升档：修 bug、体验、文案、小优化、热修 | 可直接更新 |
| `MINOR` | 中版本 | 用户可感知的新能力，或**本周功能打包**发版 | 建议更新；一般无需迁移 |
| `MAJOR` | 大版本 | **仅**破坏性变更、强制迁移、或负责人明确的产品代际 | 必须读说明；可能要迁移 |

展示文案：

```text
GuDuu OS 1.3.0
```

OEM 白牌只换产品名前缀，数字规则不变。正式发版必须是干净的 `x.y.z`（不要把 `-rc` 当正式版）。

---

## 2. 节奏与语义怎么配合

维护感**不靠每月狂涨 MAJOR**，而靠两件事：

1. 有交付就勤涨 **PATCH**（数字常动）  
2. 每周产出一份**对外更新说明**（人话比数字更有「在维护」感）

### 2.1 小版本 PATCH（勤涨，养活跃）

- 每个**有可交付改动**的工作日：发版时默认 `PATCH +1`。
- 同一天多次可交付：可多次涨 PATCH。
- 当天若已发 MINOR / MAJOR，不必再单独发 PATCH。
- **禁止**为凑数而空发版（没交付就不涨号、不硬 commit）。

### 2.2 中版本 MINOR（每周打包）

- 每个自然周至少争取 **1 次** `MINOR +1`（PATCH 归零），把本周可对外说的增量收成一版。
- 本周若已发 MAJOR，可视作已覆盖「本周中档以上更新」，MINOR 可省略。
- 本周只有热修、没有任何可对外说的新能力：只涨 PATCH 即可，**不要硬凑 MINOR**；周报仍要出（见 §7）。

### 2.3 大版本 MAJOR（克制，保信任）

- **不设「每月必须涨一次 MAJOR」。**
- 仅当出现：破坏性变更、强制数据/配置迁移、协议或 OEM 升级路径不兼容、或负责人指定代际跃迁。
- 预期频率：一年内有数次即可；多数月份可以没有 MAJOR。
- 涨 MAJOR 时 MINOR、PATCH 归零，发版说明必须写清：要不要迁移、怎么迁。

### 2.4 每月做什么（说明，不是涨号）

- 每月至少产出 **1 份「本月更新说明」**（拉本月 `release:` / DEVLOG 再加工，见 §7）。
- 月报**不要求**伴随 MAJOR；有破坏性时才升 MAJOR 并在月报里置顶「注意事项」。

### 2.5 同一次发版只升一档

```text
有破坏性 / 强制迁移 / 负责人指定代际？ → MAJOR +1，MINOR、PATCH = 0
否则本周打包新能力 / 可感知增量？     → MINOR +1，PATCH = 0
否则有可交付改动？                     → PATCH +1
```

## 3. 设计原则

1. **语义优先于凑数**：MAJOR/MINOR/PATCH 首先表达兼容性与变更体量，其次才服务发版节奏。  
2. **整栈一个号**：`cosmac.__version__`、`client/package.json`、distro/发行说明、Nexus 心跳 `version` 必须一致。  
3. **有发版才涨号**：本地草稿、未要求提交的实验 → 不涨号。  
4. **不用日期当版本号**（禁止 `2026.7.22`、`20260722` 等对外主号）。  
5. **Synapse / SDK 版本不是产品版本**，只进技术信息。  
6. **提交说明可机读**：方便「拉本周/本月变更 → 再加工即用」（§6、§7）。

---

## 4. 版本号落点

每次可交付发版对齐：

| 位置 | 用途 |
|---|---|
| `cosmac/__init__.py` → `__version__` | bot / Nexus 心跳 |
| `client/package.json` → `version` | 前端与关于页 / 管理后台 |
| distro / 发行说明 | OEM 安装升级 |

推荐同时：

| 位置 | 用途 |
|---|---|
| git tag `vX.Y.Z` | 回溯与周报/月报拉取 |
| `DEVLOG.md` 顶条 | 人话变更源 |
| commit message | 机读变更源（§6） |

---

## 5. OEM 含义（简表）

| 变动 | 对 OEM |
|---|---|
| 仅 `PATCH` | 可直接更新 |
| `MINOR` | 建议更新；一般无需迁移 |
| `MAJOR` | 必须读发版说明；按迁移文档操作（无迁移时显式写「无需迁移」） |

比较版本用标准 SemVer，勿按纯字符串字典序。

## 6. AI / 人工提交规范（写给 GitHub 的笔记）

AI 在**提交到 GitHub**时必须遵守版本规则，且笔记格式固定，便于日后拉周报/月报。

### 6.1 何时升号并提交

在负责人要求 commit / 项目约定的「可用版本提交推送」流程中：

1. 按 §2.5 判定 patch / minor / major，改齐版本落点。  
2. `DEVLOG.md` 顶部新增一条（§6.2）。  
3. commit message 用 §6.3。  
4. （推荐）打 tag：`vX.Y.Z`。  
5. 再 push；客户端有改动则按惯例 build + 部署说明。

未要求提交时：不要为凑每日 PATCH 擅自 commit。

### 6.2 DEVLOG 条目格式（强制）

```markdown
## YYYY-MM-DD — GuDuu OS X.Y.Z (patch|minor|major)

- 新增：……
- 修复：……
- 优化：……
- 变更：……（行为变化、需注意；MAJOR 时必写迁移与否）
- 决策：……（可选，内部为什么）
```

- 标题必须含产品版本号与档位 `(patch|minor|major)`。  
- 分类前缀按需使用，至少 1 条用户能听懂的说明。  
- 不写 key / IP / 密码等敏感信息。

### 6.3 Commit message 格式（强制）

```text
release: GuDuu OS X.Y.Z (patch|minor|major)

- 新增：……
- 修复：……
- 优化：……
```

- 第一行固定：`release: GuDuu OS X.Y.Z (档位)`。  
- 正文与 DEVLOG 用户可见部分对齐（可略短）。  
- 非发版类普通 commit 可不升版本号；发版相关必须走本格式。

### 6.4 同日多档

同日只需 **一次** 高档发版提交；用高档标签，正文汇总当日要点。

## 7. 「拉取本周 / 本月变更说明」工作流

负责人可说：「拉取本周变更说明」或「拉取本月更新说明，加工成对外文案」。

AI 步骤（产出应**直接可用**）：

1. **取源**（并集去重）：  
   - `git log`：区间内 `release: GuDuu OS`（兼容历史 `release: GuDuu OS`）；  
   - `DEVLOG.md`：同区间含 `GuDuu OS X.Y.Z`（或历史 GuDuu OS）的条目；  
   - tag `vX.Y.Z`（若有）。  
2. **归并**：按 `新增 / 修复 / 优化 / 变更` 合并；去掉「决策」与敏感信息。  
3. **版本跨度**：区间内最早 → 最新产品号。  
4. **输出模板**：

```markdown
# GuDuu OS 更新说明（YYYY-MM-DD ~ YYYY-MM-DD）

本周/本月版本：X.Y.Z → P.Q.R

## 新增
- …

## 修复
- …

## 优化
- …

## 注意事项
- …（仅当有「变更」、MAJOR 或迁移时；否则可整节省略）
```

- **周报**：建议每周固定产出一次（与是否涨 MINOR 无关；哪怕本周只有 PATCH）。  
- **月报**：每月至少一次；这是月度「维护感」的主载体，**不强制**伴随 MAJOR。

---

## 8. 发版操作清单（摘要）

1. 按 §2.5 选档并计算新版本号。  
2. 改 `__version__` + `client/package.json`（+ distro 说明若有）。  
3. 写 `DEVLOG.md` 顶条（§6.2）。  
4. 客户端改动则 build；需要则 `git add -f client/dist`。  
5. `git commit` 使用 §6.3。  
6. 可选 `git tag vX.Y.Z`。  
7. push / 部署；核对关于页、心跳、后台版本一致。

## 9. 起步

| 现状 | 处理 |
|---|---|
| `cosmac.__version__ = "1.0.0"` | 产品基线；下次发版起按 §2.5 递增 |
| `client` `0.1.0` | 下次发版与 cosmac **对齐同一号** |

## 10. 反例

- ❌ 日期党对外版本号  
- ❌ 客户端与 bot 版本长期不一致  
- ❌ 有可交付发版却不涨号  
- ❌ **无交付也硬凑 PATCH / MINOR / MAJOR**  
- ❌ **无破坏性却定期涨 MAJOR**（损害 OEM 信任）  
- ❌ 整周有可对外说的新能力却从不涨 MINOR、也不出周报  
- ❌ 整月既无月报、用户侧又完全看不到更新痕迹  
- ❌ 发版 commit 不写 `release: GuDuu OS X.Y.Z (档位)`  
- ❌ DEVLOG 缺版本号或 `patch|minor|major` 标签  
- ❌ 用 Synapse 版本冒充产品版本  

---

## 11. 变更本规则

1. 先改本文；  
2. 同步 `.cursor/rules/versioning.mdc` 与 `CLAUDE.md` / `AGENTS.md` 摘要；  
3. `DEVLOG.md` 记一条；  
4. 若影响 OEM 最低兼容版本逻辑，先问负责人。
